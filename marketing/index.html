The problem

A backup you can't verify
is a backup you can't trust.

Cloud sync is optimistic. It tells you what it uploaded, not whether your archive still matches the machine it came from. After a rename, a migration, or a decade of backups, the only honest answer is a full comparison.

Paths drift

Projects get reorganized, machines get retired, and folders move. A simple path check reports thousands of healthy files as missing.

Millions of rows

At 1.4 million files, a CSV and a spreadsheet stop being a strategy. You need aggregation, search, and a way to navigate the gaps.

Hashes don't line up

Cloud providers often expose MD5 while local indexers store SHA-256. Content hashing across both sides is not always available.

How it works

From snapshot to answer
in three commands.

No daemon, no database migration, no cloud API keys in a browser. Point the comparator at the listing you already have.

  1. 1

    Snapshot the cloud

    Use rclone's JSON listing. It records paths, sizes, and folder structure without downloading file contents.

  2. 2

    Compare with your index

    Run the comparator against your SQLite file index. It streams results into reports instead of holding a million rows in memory.

  3. 3

    Explore & resolve

    Open the virtual explorer, filter to what matters, and reveal counterparts side by side. Nothing is deleted or modified.

Full quickstart
quickstart.sh 
# 1 · Snapshot the cloud listing
$ rclone lsjson jotta:Archive -R > archive.json

# 2 · Compare against the local index
$ python3 scripts/compare.py \
    --db file_indexer.db \
    --archive archive.json \
    --out report

# 3 · Open the virtual explorer
$ python3 explorer/server.py --open

Browse the docs
Does it upload, move, or delete anything?

No. The comparator reads an rclone JSON listing and your SQLite index. The explorer opens the index read-only and serves a virtual view from cache. It only writes report artifacts and cache files.

What do I need to run it?

Python 3.10 or newer, rclone with a configured remote, an index database with a files table, and a provider snapshot. The server itself uses only the Python standard library — no pip install.

Why are so many “missing” files in node_modules?

File indexers commonly skip dependency and build folders such as node_modules, .next, dist, build, target, and vendor. Those files exist in the cloud but were never indexed locally. The report quantifies this so you can focus on the actionable remainder.

How are moved files matched?

The matcher looks for the same basename and exact byte size anywhere in the index, then scores candidates by shared parent folder, shared top-level folder, and path depth. If several candidates exist, the best one is shown and the rest are counted.

Can it compare file contents?

Not directly. Cloud providers often expose MD5 while local indexers store SHA-256, so the reference workflow cross-checks name, path, and size. A file renamed and resized can be reported as missing even if a copy exists — treat “possible” as needs review, not confirmed absent.

Is there a hosted demo?

No. The explorer is intentionally local: archives are large and private, and the point is to inspect your own index without sending it anywhere. The documentation includes screenshots and a complete walkthrough instead.
